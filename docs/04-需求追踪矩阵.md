# 04 · 需求追踪矩阵（v2.2）

> 配套文档：[`00-需求规格说明书.md`](00-需求规格说明书.md)（下称 PRD，需求基线）。
> 本文回答三个问题：**每条需求实现了没有、代码在哪、怎么证明**。

## 1. 维护约定

1. **PRD 的需求条目与验收标准不因实现而修改。** 实现与 PRD 不一致时，改代码或登记到 §5，不在 PRD 里"改需求迎合代码"。
2. 状态口径沿用 PRD §0.3：`已实现` = 已具备（含验证），`部分` = 主流程可用但有明确缺口，`未实现` = 待建。
3. 每条需求必须有「实现位置 + 验证证据」；只写状态不写证据的，视为未登记。
4. 新增或变更需求：先改 PRD 并升版本，再回填本表；顺序不能反。

## 4. 数据模型与枚举的实际口径

PRD §6 写于开发前，实现有 4 处结构性扩展（均为有意为之，理由见 `01` §3.1）。读 PRD 第 6 章时以本节为准：

| 项 | PRD 基线 | 交付实现 |
| --- | --- | --- |
| 业务表数量 | 16 张（§6.1 清单） | **21 张**（+ `order_items`、`banners`、`comment_likes`、`reports`、`order_snapshots`；另有 Alembic 自带的 `alembic_version`） |
| 订单商品快照 | `orders.products_info` JSON | `order_items` 明细表（`product_name/price/image/condition/quantity` 下单即固化） |
| 订单状态 | 5 种 | 6 种（+ `退款中`，`refund_prev_status` 记录驳回后回退目标） |
| 商品状态 | 3 种 | 3 种不变，另加 `is_available`（可售开关）、`is_featured`（运营加权） |
| 支付方式 | 余额/微信/支付宝/线下（首版余额+线下） | 枚举保留 4 值，`pay_options` 仅下发 **余额/线下** |
| 举报对象 | 评价、商品 | 评价、商品、**用户**（治理闭环需要） |
| 种子数据（§6.4） | 4 个平台分类、3 卖家、12 商品、2 买家、1 管理员 | **6 个平台分类**、3 卖家、12 商品、2 买家、1 管理员、**3 张轮播**、6 笔演示订单、3 条评价 |
